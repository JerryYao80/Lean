这个改法是对的，而且你的19%这个数字本身就是一个很好的自检证据——它和"365/252口径失配"的理论值高度吻合，说明你诊断到的很可能不是"两种都合理只是选一个"，而是当前代码里存在一个**分子分母不匹配的真实bug**。

**为什么是这个bug（而不是单纯的口径偏好）**

如果之前Python的T是用`calendar_dte`（自然日）作分子，却用252做分母（即混用了"自然日计数+交易日年化基数"），那么：

T_current = calendar_dte / 252
T_correct = calendar_dte / 365

T_current / T_correct = 365/252 ≈ 1.448

期权定价里，ATM附近IV与1/√T近似成正比（固定期权价格反解隐含波动率时），所以修正后：

IV_new/IV_old ≈ √1.448 ≈ 1.203

也就是约**+20.3%**，和你观测到的~19%非常接近（差异来自非ATM点和实际曲面插值的非线性）。这基本确认了根因就是T的分子分母口径不一致，而不是两种自洽方案里选一个更"正确"的问题——之前的T被系统性高估了约45%，导致IV被系统性低估。

**改法本身没问题，但有一处要单独确认，不要连带改错**

Realized Volatility（RV）的年化不需要跟着改成365。RV来自日收益率的方差累积，只在交易日发生，用`sqrt(252)`年化是行业标准（CBOE自己算VIX时T用calendar/365，但底层用的是分钟级方差累积，不是简单的"改分母"能完全对齐，这个后面细讲）。IV的T用calendar/365、RV用252年化，两者年化基数不同**并不是不一致**，这是业界的常规做法（vol risk premium = IV - RV 直接比较年化后的两个数，尽管底层时间尺度不同）。所以：
- `compute_atm_iv` / `compute_25delta_iv` / `iv_surface_skew` / `vix_for_term` 里的T：改
- RV计算模块：**不要**跟着改成365，除非你现在RV那边本来就是对的252

**关于CBOE对齐的一个细节**

CBOE VIX的T实际公式是分钟级精度：
T = [N_今天剩余分钟 + N_中间自然日×1440 + N_到期日已过分钟] / (365×1440)

如果你现在只是简单`calendar_dte/365`（整数天），在近月合约（<7天）上误差会被放大，可能造成短端VIX仍有小幅偏差。如果你的应用对短端精度要求高（比如你的RL风控层用短期IV做尾部风险特征），建议至少把当天剩余交易时间以分钟折算进`calendar_dte`，而不是用整数自然日差。

**建议的验证步骤**

1. 挑1-2个历史日期，用改前/改后T分别算50ETF期权ATM IV，验证比值确实收敛到√(365/252)附近而非任意其他值——如果不是，说明不只是这一个bug
2. 找一个外部IV源（比如公开的50ETF波动率指数历史值）做同日对比，改后应该显著更接近
3. `iv_rv_z_score`阈值重新校准时，建议用改口径后至少3-6个月的滚动窗口重新算z-score分布，而不是简单线性平移旧阈值×1.2，因为IV-RV spread的分布形状（不只是均值）也会变
。锁定"改前T值→改后T值→IV变化比例"这条链路，防止以后再有人不小心改动其中一处口径破坏自洽性
