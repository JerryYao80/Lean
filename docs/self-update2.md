1. 三道门是否够，要不要加"对比基线策略"门
不够。编译/单测/回测回归这三道门验证的是"代码没写坏、没退化"，但没有验证"这次优化到底有没有效"。建议加第四道门，且要卡两个基线，不是一个：
对比优化前的自己（同策略上一版本）——防止这次调参是负优化
对比买入持有 / 等权基准——防止整个策略框架本身跑不赢无脑基准，这种情况下再怎么优化超参都是在优化一个错误方向
第四道门建议用统计显著性检验而不是简单数值比大小（比如两组回测收益序列做 bootstrap 或 White's Reality Check），否则"优化后 Sharpe 从 1.1 到 1.15"这种噪声级别的提升会被误判为真实改进——这恰好是 DSR 想解决的同一类问题，你这里等于是把 DSR 的逻辑再搬一遍用于版本对比。
2. OOS Sharpe ≥ IS×0.6 vs DSR 绝对值阈值
这个相对阈值本身有个逻辑漏洞：如果 IS Sharpe 因为过拟合虚高到 3.0，那 OOS 阈值线是 1.8，这个门槛本身就是被过拟合污染出来的，等于用"作弊的分数"去定合格线。
更合理的做法是两个阈值都要，缺一不可：
OOS Sharpe 的绝对下限（比如 ≥ 0.8，具体看你的策略类型和你能接受的资金曲线）——防止"虽然衰减比例合格但绝对水平已经不能用"
IS→OOS 的衰减比例（你现在的 0.6）——防止"绝对值达标但衰减剧烈，说明泛化差"
如果已经在用 DSR 做 reward，OOS 阶段应该直接算 DSR 而不是普通 Sharpe，因为 DSR 本身已经把"你测试了多少次"这个信息编码进去了，普通 Sharpe 的 0.6 比例阈值没有考虑你在 Layer A 到底扫了多少组超参——扫得越多，虚高越严重，固定 0.6 这个比例对"扫了 10 次"和"扫了 10000 次"的试验是不公平的同一把尺子。
3. state_trace_sample.jsonl commit 进 repo 还是 CI 动态生成
看这个文件的用途决定，如果没看到 §5 我只能按经验给分叉判断：
如果它是用于回归测试的黄金样本（fixture，验证 Lean/PPO 交互格式没有breaking change）→ 应该 commit，且要小（几十条到几百条），因为你需要它在未来任何时候都可复现同样的断言，动态生成会导致这个文件本身也可能因为环境/依赖变化而漂移，失去"基线"意义。
如果它是每次回测都会变化的产出物（比如记录本次训练用的实际状态序列，体量大且频繁变化）→ 不该 commit，应该 CI 动态生成后作为 artifact 上传（GitHub Actions artifact / S3），repo 只保留生成脚本，否则 repo 体积膨胀且 diff 噪音巨大，git blame 也失去意义。
一个折中方案：repo 里 commit 一个极小的 schema 校验样本（3-5 条，纯粹验证字段格式），完整的 trace 数据走 CI 动态生成 + 外部存储
