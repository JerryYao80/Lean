这个诊断和修复做得很扎实——尤其是没有止步于"reward 平稳了"就结案,而是继续往下追问"为什么 30 个 trial 全是 0.209",这一步很关键,因为如果当时就此打住,你会得到一个"技术上正确但实际上什么都没测出来"的优化器。

**下一步顺序,我建议:**

**先做 1(参数传播修复),但在写代码前先加一个诊断断言,别直接跳到"扩大窗口"。**

理由:现在有两个假设在竞争——(a) 参数确实传不进去(CLI bug),(b) 参数传进去了但当前窗口/策略不敏感。你的报告目前是把两者都当成了成立的结论,但实际上还没有一个干净的实验把它们分开验证过。如果 (a) 修复后仍然全是 0.209,才能真正确认是 (b)。如果现在就跳去扩大窗口或换策略,一旦后面还是不变,你不知道是新窗口不敏感,还是 config 字段传参依然有别的坑(比如 JSON 序列化格式、LEAN 读取时机、参数名大小写/连字符 vs 下划线不匹配等)。

**具体建议的验证步骤:**

1. 改完 `lean_runner.py` 用 config 字段传参后,**先不要跑 30 trials**,而是手动构造 2-3 个参数取值差异巨大的极端组(比如 `max-position-weight` 从 0.1 和 0.9 分别跑一次),直接跑两次单独的 LEAN backtest(不经过 Optuna),对比订单数/Sharpe 是否出现任何变化。这一步几秒钟能做,却能把"传参管道是否work"这个变量彻底隔离掉,不用等 30 trials 跑完才发现还是老问题。

2. 如果这两次手动极端对比出现了差异 → 说明传参修复生效,直接重跑 30 trials 观察 best Sharpe 是否随 N 改善(对应你说的任务 3)。

3. 如果这两次手动对比依然没有任何差异 → 说明问题不在传参机制,而在于策略本身(L2 Alpha 阈值确实在这个窗口从不触发,或者 LEAN 读取 config 里 parameters 字段的 key 名和策略代码里读取的 key 名对不上——这个也值得直接 grep 一下策略代码里 `GetParameter(...)` 用的 key 字符串,和你 config 里写的 key 是否完全一致,包括大小写和连字符/下划线)。这时候再决定是换窗口还是换策略,而不是两个假设都先动。

**关于换窗口 vs 换策略**,我倾向于**换 VarStrategy 而不是仅仅拉长 OptionVolArb5Layer 的窗口**——拉长窗口只是让阈值触发次数变多,但如果 4 个月里都不触发,可能是因为这策略的信号本身在正常市场状态下就是稀疏事件驱动型的(iv-rv-z 只在极端波动期触发),窗口拉到 1-2 年也可能大部分时间还是不触发,你其实是在赌能不能覆盖到一次极端事件。VarStrategy 参数直接控制风控敏感度,理论上任何窗口都应该看到参数敏感性,是更干净的"优化器探索能力"验证对象。
