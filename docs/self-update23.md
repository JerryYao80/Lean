## 结论:A + C 并行,B 的核心机制(数值降权)不采用,但 B 的"字段化"思路值得借用

## 为什么不是单选 B

B 的问题在于:置 0 造成的不是"这个 policy 不太可靠",而是"这个 policy 学到的是一个在系统性错误假设下的确定性映射"——它对置 0 状态给出的动作是**自信的、错误的**,不是"噪声大、置信度低"。数值降权(reliability_level 低权重)处理的是"我不太信任这个结果,少用一点",但这里真正需要的是"这个结果本身可能是错的,该阶段不能用",这是二元判断,不是权重问题。降权会给人一种"已经妥善处理了"的错觉,但风控 policy 一旦被选中执行(哪怕权重低),置 0 字段带来的错误映射依然会直接作用在真实仓位上。

## A 立即执行,但把它从"人工记住"升级成"自动门禁"

单纯靠人工把这两个策略移出候选、"标记为实验性"——这个标记本身很容易随时间被遗忘或在下一次审计前失效(就像这次如果不做审计,置 0 字段的问题会一直被"已知简化"这个措辞悄悄带过)。

建议把 B 里"加字段"这个思路**只用于自动化拦截**,而不是用于加权:在 manifest.yaml 里加一个布尔状态字段(比如 `rl_state_completeness: full | partial`),`manifest_lint.py`(门 0)直接检查这个字段——`partial` 的策略在 CI 层面就不允许进入灰度部署流程,不需要每次靠人记得"哦这个策略字段还没补"。这样"移出候选"从一次性人工动作变成了框架能自动强制执行的规则,以后新策略接入时如果漏填字段也会被自动拦下,而不是要等下一次审计才发现。

## C 同时开工,但注意两点

**第一,不要用现在的 PPO pipeline 直接重训这两个策略**。上一轮已经确认 Layer C 的地基(gym_env 是否真 MDP)本身需要修——如果按计划先做"离线 RL + OPE"或后续"轻量 MDP 模拟器",那么给 BarraCNE5V4/OvernightAnomaly 补完真实字段后,应该用**修复后的 pipeline**重训,而不是先用旧 PPO 训一遍、之后再推倒重来。两个修复(地基 + 字段)最终要在同一套新 pipeline 上收口,顺序上是"先修地基方法论,字段修复完成后一起用新 pipeline 训",不是两条独立线各跑各的。

**第二,复制 OptionVolArb5Layer 的接入模式前,先核实这个参照本身没问题**。现在的逻辑是"OptionVolArb5Layer 已填真实值,照着抄就行",但这个参照如果本身在 `pnl_1d`/`days_held`/`drawdown` 的计算上有细节错误(比如持仓天数计算的边界情况、drawdown 用的净值口径是否和 Layer A 回测统计口径一致),照抄会把同一个错误复制到另外两个策略上。建议花一点时间抽查 OptionVolArb5Layer 这几个字段的计算逻辑是否正确,再作为模板推广,而不是默认它"是真实值就等于是对的"。

## 顺序建议

1. 现在:A(移出候选)+ manifest 自动化门禁——成本几乎为零,先止血。
2. 与 Layer C 地基修复(离线 RL/MDP 模拟器)并行:审计 OptionVolArb5Layer 的字段计算逻辑是否正确。
3. 地基修复方法论确定后:补 BarraCNE5V4/OvernightAnomaly 真实字段,用新 pipeline 重训,而不是用当前 PPO 重训一遍再返工。
